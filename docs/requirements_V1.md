## 1. 系统概览

### 1.1 一句话定位

**把设备维护过程中产生的故障记录和维修经验，沉淀为可检索的知识库，让历史数据指导未来的维修决策。**

### 1.2 客户画像

制造业工厂的设备管理者，日常管理**传感器、PLC、风机、电机、变频器**等各类自动化设备。核心团队包括：管理员（统筹）、工程师（制定计划 + 解决故障）、技术员（执行巡检 + 发现故障）。

### 1.3 核心痛点与设计回应

| 痛点 | 为什么这样设计 |
|------|------|
| 老师傅离职，维修经验跟着走 | 每个故障的「原因 + 解决方法」强制录入系统，人走了知识留下 |
| 同类故障反复发生，每次从头排查 | 录入新故障时自动推荐相似历史案例，直接看到上次怎么修的 |
| 设备维护靠人记，经常漏检 | 维护计划自动倒计时 + 邮件提醒，到时间就催 |
| 故障处理没追踪，不知道谁在管 | 故障状态流转（待处理→处理中→已解决→已关闭），每个状态有责任人 |

### 1.4 模块全景图

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   用户管理    │────▶│   权限控制    │◀────│   系统日志    │
└──────────────┘     └──────────────┘     └──────────────┘
                            │
       ┌────────────────────┼────────────────────┐
       ▼                    ▼                    ▼
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   设备管理    │     │   维护管理    │     │   故障管理    │
│  (台账+分类)  │     │ (计划+执行)   │     │ (录入+处理)   │
└──────┬───────┘     └──────┬───────┘     └──────┬───────┘
       │                    │                    │
       │            巡检异常自动生成故障 ◀────────┘
       │                    │                    │
       └────────────────────┼────────────────────┘
                            │
                            ▼
                   ┌──────────────┐     ┌──────────────┐
                   │   知识库      │◀────│   培训管理    │
                   │ (历史故障检索) │────▶│ (案例作教材)  │
                   └──────────────┘     └──────────────┘
```

**模块关系说明：**

- **设备管理**是基础，所有维护和故障都关联到具体设备
- **维护管理**驱动日常巡检，巡检中发现异常自动生成故障记录
- **故障管理**记录故障和处理过程，是知识库的数据来源
- **知识库**从故障记录中沉淀，反过来指导故障排查
- **培训管理**引用知识库中的典型案例作为教材
- **用户管理**控制谁能做什么，贯穿所有模块

## 2. 核心业务流程

### 2.1 主流程：从巡检到知识沉淀

```
工程师制定维护计划
        │
        ▼
系统自动倒计时 + 到期邮件提醒
        │
        ▼
技术员执行巡检 ──正常──▶ 完成，计算下次维护时间
        │
       异常
        │
        ▼
自动生成故障记录 ──────────────┐
        │                      │
        ▼                      │
系统推荐相似历史故障 ──────────┤
        │                      │
        ▼                      │
技术员参考历史方案排查 ────────┤  知识库
        │                      │
        ▼                      │
工程师接手处理 ────────────────┤
        │                      │
        ▼                      │
录入故障原因 + 解决方法 ───────┘
        │
        ▼
沉淀为知识条目，下次同类故障可检索
```

### 2.2 子流程：故障报修

```
技术员发现设备异常
        │
        ▼
录入故障现象 ──▶ 系统实时推荐相似历史故障
        │              │
        │              ▼
        │        技术员查看推荐：
        │        "上次同样的风机异响，是轴承缺油，加润滑脂就好了"
        │        "我先检查一下轴承，如果是同样问题就不用麻烦工程师了"
        │
        ▼
提交故障记录
        │
        ▼
工程师接手 → 参考历史方案 → 维修 → 录入原因和解决方法 → 完成
```

## 3. 用户与权限管理

### 3.1 为什么这样设计

三种角色对应工厂实际的组织分工：

- **管理员**：部门主管，管人、管配置、看报表
- **工程师**：技术骨干，定计划、修设备、沉淀知识
- **技术员**：一线执行，巡检设备、发现问题、参考历史记录

### 3.2 角色定义

| 角色 | 职责 | 核心权限 |
|------|------|------|
| 管理员 | 统筹管理 | 创建账户、配置系统、查看所有数据、导出报表 |
| 工程师 | 技术管理 | 创建设备和维护计划、处理故障、编辑知识库、导出数据 |
| 技术员 | 一线执行 | 执行巡检、录入故障、查询历史记录（不能删除、不能导出） |

### 3.3 账户管理流程

```
管理员创建账户
      │
      ├── 填写：用户名、密码、姓名、工号、邮箱、手机号
      ├── 选择：角色（管理员/工程师/技术员）
      ├── 选择：工作类型（电气/机械/自动化/综合）
      │         └── 工作类型决定该账户能管理哪些设备
      │
      ▼
账户创建成功，状态为「启用」
      │
      ▼
用户首次登录 → 强制修改密码
      │
      ▼
正常使用
      │
      ├── 密码90天过期 → 提醒修改
      ├── 忘记密码 → 邮箱重置链接
      │
      ▼
员工离职/转岗 → 管理员禁用账户
      │
      ▼
账户禁用，不可登录，但历史操作记录保留
（不物理删除，防止历史记录中「修改人」变成空）
```

### 3.4 工作类型

工作类型决定了一个工程师/技术员**能看到和操作哪些设备**。

| 工作类型 | 可管理的设备类型 |
|------|------|
| 电气 | 电机、变频器、配电柜等电气设备 |
| 机械 | 风机、传动装置、气动元件等机械设备 |
| 自动化 | PLC、传感器、HMI、伺服驱动等自动化设备 |
| 综合 | 所有设备 |

> **设计意图**：电气工程师不需要看到机械风机的数据，减少信息干扰；同时防止误操作。

## 4. 设备管理

### 4.1 为什么这样设计

设备是系统的数据基础，所有后续操作（维护、故障、知识库）都挂在设备上。设备台账相当于「设备身份证」，记录设备从采购到报废的完整生命周期。

### 4.2 设备类型

系统管理 **11 种**设备类型，每种有通用字段 + 特有字段：

| 设备类型 | 举例 | 特有字段 |
|------|------|------|
| 传感器 | 温度传感器、压力传感器、光电开关 | 测量类型、量程、输出信号、精度 |
| PLC | S7-1200、FX5U | 品牌、CPU型号、IP地址、通信协议、I/O点数 |
| 风机 | 离心风机、轴流风机 | 风量、风压、功率、转速、驱动方式 |
| 电机 | 三相异步电机、伺服电机 | 功率、电压、电流、转速、绝缘等级、防护等级 |
| 变频器 | 各类变频器 | 功率、输入/输出电压、控制方式、通信接口 |
| HMI | 触摸屏 | 屏幕尺寸、品牌、通信接口 |
| 伺服驱动 | 伺服驱动器 | 功率、扭矩、编码器类型 |
| 液压 | 液压泵、液压阀 | 压力、流量、介质 |
| 气动 | 空压机、气缸 | 压力、流量 |
| 输送 | 传送带、提升机 | 速度、宽度、负载 |
| 其他 | 未分类设备 | 自定义参数 |

> **设计意图**：不同设备关注点不同。传感器关心量程和精度，PLC关心IP地址和程序版本，风机关心风量和转速。特有字段让录入更精准，也让后续检索更有效。

### 4.3 设备生命周期

```
创建设备（录入台账）
      │
      ▼
正常 ──────────────────────────────────────────────┐
  │                                                │
  ├── 维护到期 → 自动变为「待维护」                   │
  │      │                                         │
  │      └── 维护完成 → 自动恢复「正常」              │
  │                                                │
  ├── 巡检发现异常 / 主动报修 → 变为「故障」           │
  │      │                                         │
  │      └── 故障修复 → 手动恢复「正常」              │
  │                                                │
  ├── 计划停机 / 非计划停机 → 手动变为「停机」         │
  │      │                                         │
  │      └── 恢复运行 → 手动恢复「正常」              │
  │                                                │
  └── 报废 → 终态，不可逆 ◀─────────────────────────┘
```

> **设计意图**：状态由系统自动驱动（维护到期→待维护）或人工操作（停机→正常），减少人工维护状态的工作量，同时保证状态准确性。

### 4.4 层级分类

```
工厂
├── 一车间
│   ├── 产线A
│   │   └── 工位A1
│   │       ├── 温度传感器-PT100
│   │       └── PLC-S7-1200
│   └── 产线B
└── 公用设施
    └── 空压站
        └── 离心风机-CF-500
```

- 最多 5 级，只有叶子节点可以挂设备
- 分类可增删改，删除前需确保无子节点和设备

### 4.5 文件附件

每个设备可上传多个文件，按标签分类：

| 标签 | 用途 |
|------|------|
| 设备照片 | 设备外观 |
| 铭牌照片 | 铭牌信息 |
| 说明书 | 设备手册 |
| 电气图纸 | 电路图 |
| PLC程序 | 程序备份文件 |
| 其他 | — |

> **设计意图**：现场维修时，工程师可以直接在系统中查看设备图纸和说明书，不用翻找纸质文件。

## 5. 维护管理

### 5.1 为什么这样设计

设备维护的核心矛盾是：**该维护的时候没人记得，维护完了没人记录**。系统通过「计划 → 倒计时 → 提醒 → 执行 → 记录」的闭环，确保每一步都落实。

### 5.2 完整流程

```
【第一步：创建维护计划】（工程师操作）
      │
      │  填写：计划名称、维护内容（图文SOP）、关联设备、维护周期
      │  定义：检查项目清单（逐项列出检查内容 + 检查标准 + 标准配图）
      │
      ▼
【第二步：计划生效】
      │
      │  系统自动计算首次维护时间
      │  计划状态：启用
      │
      ▼
【第三步：倒计时 + 提醒】
      │
      │  仪表盘显示倒计时：距下次维护还有 X 天
      │  按管理员配置的通知时间点发送邮件提醒 + 站内通知
      │  （管理员可自定义通知时间，如到期前3天、1天，支持配置多个时间点）
      │  到期当天：设备状态自动变为「待维护」
      │
      ▼
【第四步：执行巡检】（技术员操作）
      │
      │  技术员登录 → 查看「我的待维护任务」
      │  逐项检查：
      │
      ├── 正常 → 点击「正常」→ 可上传现场照片
      │
      └── 异常 → 点击「异常」→ 必填异常描述 + 异常照片
      │
      ▼
【第五步：提交维护记录】
      │
      │  全部检查完毕 → 提交
      │  系统自动计算下次维护时间 = 当前时间 + 维护周期
      │
      ├── 全部正常 → 完成
      │
      └── 有异常项 → 自动生成故障记录（异常描述、照片、设备自动带入）
      │
      ▼
【第六步：超时处理】
      │
      │  超过计划时间3天未执行 → 标记「超时未维护」
      │  设备状态变为「待维护」
      │  每天发送提醒通知
```

### 5.3 维护计划版本管理

```
工程师修改维护计划
      │
      ▼
自动生成新版本（V1.0 → V1.1）
      │
      ▼
历史版本保留，已执行的维护记录关联当时的版本号
```

> **设计意图**：维护计划会迭代优化。保留版本历史，可以追溯「某次维护是按哪个版本的SOP执行的」。

### 5.4 维护完成率统计

```
按时完成率 = 按时完成数 / 应完成数 × 100%

统计维度：
- 按设备统计（哪个设备维护最不及时）
- 按设备类型统计（PLC vs 风机 vs 传感器）
- 按工程师统计（哪个工程师负责的设备维护最到位）
- 按时间范围统计（本月 vs 上月 vs 本季度）
```

## 6. 故障管理

### 6.1 为什么这样设计

故障管理的核心价值不在于「记录」，而在于「复用」。每一次故障的「原因」和「解决方法」都是宝贵的经验，应该被系统化地沉淀下来，让下一个遇到同类故障的人能快速找到答案。

### 6.2 完整流程

```
【第一步：发现故障】（技术员操作）
      │
      │  来源一：巡检发现异常 → 自动生成故障草稿（异常信息已填入）
      │  来源二：主动报修 → 手动录入故障
      │
      ▼
【第二步：录入故障现象】
      │
      │  填写故障描述（如"风机运行时异响，轴承温度偏高到85℃"）
      │
      │  ┌─────────────────────────────────────────┐
      │  │  💡 系统实时推荐相似历史故障              │
      │  │                                         │
      │  │  相似故障1：风机异响 — 轴承磨损（90%相似） │
      │  │  解决方法：更换SKF 6205轴承，加注润滑脂    │
      │  │                                         │
      │  │  相似故障2：轴承温度高 — 缺油（75%相似）   │
      │  │  解决方法：补充高温润滑脂                  │
      │  └─────────────────────────────────────────┘
      │
      │  选择故障系统、故障位置、故障级别、关联设备
      │  上传故障现场照片
      │  提交故障记录
      │
      ▼
【第三步：故障处理】（工程师操作）
      │
      │  工程师收到通知 → 查看故障详情
      │  查看系统推荐的相似历史故障（参考过往方案）
      │  现场排查 → 维修
      │
      ├── 简单问题：技术员参考历史方案自己解决
      │     （如"缺油，加润滑脂就行"，不用等工程师）
      │
      └── 复杂问题：工程师接手处理
      │
      ▼
【第四步：录入处理结果】（工程师操作）
      │
      │  必填：故障原因（根因分析）
      │  必填：处理方法（详细步骤，后人可参考）
      │  可选：处理照片、消耗备件、停机时长
      │  可选：标记为「典型故障案例」
      │
      ▼
【第五步：沉淀为知识】
      │
      │  故障原因 + 处理方法 + 照片 → 自动进入知识库
      │  系统提取关键词，建立全文索引
      │  下次同类故障可快速检索
```

### 6.3 故障状态流转

```
待处理 ──→ 处理中 ──→ 已解决 ──→ 已关闭
  ↑          │           │
  └──────────┴───────────┘
        （重新打开）
```

| 状态 | 含义 | 谁来操作 |
|------|------|------|
| 待处理 | 故障已上报，等待处理 | 技术员提交后自动进入 |
| 处理中 | 工程师正在处理 | 工程师点击「接手处理」 |
| 已解决 | 已修复，待确认 | 工程师录入解决方案后 |
| 已关闭 | 确认修复，归档 | 管理员/工程师点击「关闭」 |

> **设计意图**：每个状态有明确的责任人，不会出现「故障报了但没人管」的情况。

### 6.4 处理时效（SLA）

| 故障级别 | 必须响应 | 必须解决 |
|------|------|------|
| 严重（停产） | 30分钟内 | 4小时内 |
| 一般（降效） | 2小时内 | 24小时内 |
| 轻微（不影响） | 8小时内 | 72小时内 |

超时自动标记，发送提醒。

## 7. 历史维修知识库

### 7.1 为什么这样设计（核心）

这是整个系统最有价值的模块。

**场景还原**：凌晨两点，产线风机异响，值班技术员是新人，不知道怎么办。他打开系统，搜索「风机 异响」，系统返回 3 条历史记录：

1. 去年 12 月，同型号风机，轴承磨损→更换轴承
2. 今年 3 月，同类风机，叶轮积灰→清理叶轮
3. 今年 6 月，同车间风机，皮带松动→张紧皮带

技术员按照记录逐一排查，发现是皮带松动，调整后恢复正常。**整个过程没有打电话叫醒工程师，10 分钟解决问题。**

这就是知识库的价值：**把老师傅的经验留在系统里，让新人也能快速上手。**

### 7.2 知识沉淀流程

```
故障已解决
      │
      ▼
工程师录入「故障原因」+「处理方法」
      │
      ▼
系统自动执行：
  1. 提取关键词（风机、异响、轴承、温度高）
  2. 建立全文索引
  3. 归类到：设备类型=风机、故障系统=机械
  4. 自动生成标签：#风机 #机械故障 #轴承 #异响
      │
      ▼
工程师可选操作：
  1. 标记为「典型故障案例」（有价值的案例优先展示）
  2. 添加自定义标签
      │
      ▼
知识条目进入知识库，可被全局检索
```

### 7.3 知识检索

**全文搜索**：输入任意关键词（设备名、故障现象、原因），搜索所有历史故障记录。

**筛选条件**：设备类型、故障系统、故障级别、时间范围、是否典型案例。

**智能推荐**：录入新故障时，系统自动分析描述，匹配相似历史故障，展示原因和解决方法。

### 7.4 设备维修履历

每个设备详情页展示完整维修时间线：

```
离心风机-CF-500 维修履历
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2025-03-20  ● 叶轮异响 → 清理积灰 → 解决
2025-06-05  ● 轴承温度高 → 补充润滑脂 → 解决
2025-09-01  ● 异响+温度高 → 更换轴承 → 解决
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
累计故障：3次  |  常见故障：轴承问题  |  累计停机：8小时
```

> **设计意图**：一眼看出这个设备「得过什么病、怎么治的、是不是老毛病又犯了」。如果某个设备频繁出现同类故障，说明需要从根本上解决问题，而不是一直修修补补。

## 8. 培训管理

### 8.1 为什么这样设计

原始需求明确提到「设备检修培训记录与培训」。系统的培训模块与其他培训系统不同之处在于：**培训素材直接来自知识库中的真实故障案例**。

### 8.2 流程

```
创建培训课程
      │
      ├── 填写课程信息（名称、类型、内容、时长）
      ├── 上传培训资料（PDF/PPT/视频）
      └── 关联典型故障案例（从知识库中选择）
      │
      ▼
组织培训
      │
      ├── 记录培训时间、讲师、地点、参与人员
      └── 上传现场照片
      │
      ▼
考核
      │
      ├── 记录考核方式（笔试/实操/口试）
      ├── 记录成绩、是否合格
      └── 不合格需复训
      │
      ▼
培训档案
      └── 每人可查看自己的培训履历（参加过哪些培训、成绩如何）
```

> **设计意图**：新员工入职培训时，直接学习系统中沉淀的真实故障案例，比看教科书更贴近实际工作。

## 9. 仪表盘

### 9.1 为什么这样设计

仪表盘是系统首页，解决「打开系统先看什么」的问题。不同角色看到不同的关键信息。

### 9.2 内容

| 区域 | 内容 | 说明 |
|------|------|------|
| 统计卡片 | 设备总数、正常/故障/待维护数量、今日待办 | 一眼掌握全局 |
| 待办提醒 | 待维护任务、待处理故障、超时任务 | 该做什么，优先级排序 |
| 趋势图表 | 故障趋势、故障分布、维护完成率 | 看趋势，发现问题 |
| 快捷入口 | 新建故障、搜索知识库、我的待办 | 高频操作一键到达 |

## 10. 辅助功能

### 10.1 数据导出

| 导出内容 | 格式 | 权限 |
|------|------|------|
| 设备台账 | Excel | 管理员、工程师 |
| 维护记录 | Excel | 管理员、工程师 |
| 故障记录（含解决方法） | Excel | 管理员、工程师 |
| 知识库 | Excel | 管理员、工程师 |

### 10.2 数据导入

| 导入内容 | 格式 | 说明 |
|------|------|------|
| 设备台账 | Excel | 批量导入设备，下载模板→填写→上传→预览→确认导入 |
| 分类结构 | Excel | 批量导入层级分类 |

### 10.3 邮件通知

#### 10.3.1 SMTP 配置（管理员）

管理员在系统设置中配置 SMTP 邮件服务器：SMTP 地址、端口、发件人邮箱、用户名/密码、SSL/TLS，支持发送测试邮件验证配置。

#### 10.3.2 通知接收人

管理员维护通知接收人邮箱列表，支持按工作类型分组（电气组、机械组等），不同维护计划可指定不同的接收人。

#### 10.3.3 通知触发事件

| 事件 | 时机 |
|------|------|
| 维护到期 | 管理员自定义通知时间点（默认到期前3天、1天），支持配置多个时间点 |
| 维护超时 | 超时后每天 |
| 故障上报 | 立即 |
| 故障超时 | 超时后每4小时 |

#### 10.3.4 维护到期通知时间自定义

管理员可在系统设置中配置维护到期通知的提前时间：

- 支持配置多个通知时间点，如：到期前 7天、3天、1天、当天
- 每个时间点独立开关（可单独启用/禁用）
- 配置示例：`[7, 3, 1]` 表示到期前7天、3天、1天各发送一次通知
- 默认值：到期前 3天、1天

### 10.4 系统日志

记录所有增删改操作（谁、什么时候、做了什么、IP地址），保留180天，不可删除。
