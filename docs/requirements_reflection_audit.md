## 1. 第一次反省：业务场景闭环、边界漏洞与隐式需求审查

### 1.1 反省焦点：从实际工厂生产环境审视业务全链路

在初步的需求梳理中，我们梳理了设备、维护、故障、知识库、培训五个核心模块。但在制造业实际严苛的生产环境中，往往存在大量处于“灰色地带”的隐式需求与边界场景。

### 1.2 发现的隐式需求与漏洞清单

#### 漏洞 1：设备物理工位变更与历史维保档案的归属冲突
* **现象与痛点**：在汽车、电子等现代制造产线中，设备搬迁、工位调换（如将A产线的备用离心风机换到B产线）极为频繁。如果设备与位置层级树采用简单硬编码绑定，一旦设备更换工位，其历史发生的故障到底属于“原工位”还是“原设备”？
* **深入反省**：
  * 设备台账是资产实体（包含出厂SN码），而位置树是物理空间实体（车间-产线-工位）。
  * 若直接修改设备的位置外键，历史故障报表在按产线统计时将发生失真。
* **设计补齐对策**：
  * 在数据库设计中，设备维护当前所处工位 `current_location_id`。
  * 所有的巡检记录表 (`maintenance_record`) 和故障单表 (`fault_record`) 必须**在生成时刻对物理工位进行历史快照固化 (`snapshot_location_id`)**。
  * 增加设备工位变动履历追踪表，支持设备调拨与位置迁移。

#### 漏洞 2：跨专业复合设备的管理死锁问题
* **现象与痛点**：需求中设定了“电气、机械、自动化、综合”四种工作类型，并规定工作类型决定可管理的设备范围（例如电气工程师只能管理电机、变频器）。然而，实际工厂中大量自动化设备是高度集成的机电一体化设备（例如带有复杂气动机械手和视觉相机的 PLC 控制包装机）。
* **深入反省**：
  * 如果机械技术员巡检时发现了电气故障，或者电气工程师处理故障时发现机械导轨变形，由于工作类型硬性隔离，是否会导致无法报修或无法协同？
* **设计补齐对策**：
  * 故障上报与巡检时，允许技术员跨专业发起“协作报修”或选择“综合工单池”。
  * 故障单模型增加“协同专业 (`cross_discipline_flag`)”与“转派/指派协作”流程，避免权限隔离变成部门墙。

#### 漏洞 3：设备停机与报废状态下的维护调度冲突
* **现象与痛点**：需求定义了设备生命周期（正常、待维护、故障、停机、报废）。但未定义当设备处于“长期停机”或“已报废”时，系统维护计划调度器应如何行为。
* **深入反省**：
  * 若一台电机停机大修 3 个月，定时调度引擎仍每天计算倒计时并不断发送到期催办邮件，将严重干扰运维人员。
  * 若报废设备仍出现在待办任务中，将导致技术员无法消警。
* **设计补齐对策**：
  * 在维护调度引擎中增加前置状态拦截：当设备状态为 `Shutdown (停机)` 时，自动冻结其维护倒计时，并记录挂起时间；恢复正常运行时顺延下次维护日期。
  * 当设备进入 `Scrapped (报废)` 状态时，自动将其从所有关联的维护计划中移除，并将未完成的待办任务自动作废归档。

#### 漏洞 4：技术员“简单故障自主排查”与数据闭环的管控漏洞
* **现象与痛点**：requirements_V1.md 提到“简单故障技术员参考历史方案自己解决（如缺油，加润滑脂），不用等工程师”。
* **深入反省**：
  * 如果技术员可以直接将故障单从“待处理”变为“已关闭”，缺乏防错与复核机制，可能导致现场重大隐患被掩盖（如技术员误以为只是缺油，实则是轴承已经碎裂破损），也可能导致故障原因胡乱填写污染知识库。
* **设计补齐对策**：
  * 设计轻量级复核状态流：技术员自修完成后，故障单状态跃迁至 `已解决(待复核)`。
  * 责任工程师收到通知后可在 1 分钟内快速在线确认，确认无误点击 `归档关闭`，并由工程师校验根因与处理步骤是否达到入库标准。

## 2. 第二次反省：工业现场边缘条件、高可靠性与数据一致性审查

### 2.1 反省焦点：底层事务、高并发突发与分布式可靠性

在生产制造企业，工厂网络抖动、工控平板离线、服务器断电重启是常见工况。必须从技术架构、持久层事务与并发竞争角度审视系统的鲁棒性。

### 2.2 发现的技术风险与强化清单

#### 风险 1：巡检异常联锁派发故障单的“断裂风险”
* **现象与技术隐患**：需求规格 REQ-MNT-008 要求“技术员提交巡检表单时，若存在异常项，系统自动联锁生成一条故障单”。如果在高并发或网络抖动情况下，巡检记录先插入成功，但生成故障单时发生数据库锁超时或网络断开，会导致“巡检显示异常但没有任何故障单被创建”的致命数据断裂。
* **深入反省**：
  * 必须保证业务操作的 ACID 原子性。
  * 不能依赖前端分步调用两个 API（先调提交巡检，再调新建故障）。
* **设计补齐对策**：
  * 后端提供单一聚合接口 `POST /api/v1/inspections/submit`。
  * 在数据库单事务（`@Transactional` 或 `BEGIN ... COMMIT`）中完成：
    1. 校验并写入 `inspection_records` 及明细子表；
    2. 检测到异常项时，即刻构造 `fault_records` 实体并持久化；
    3. 将新生成的 `fault_id` 反向回填至巡检明细表中作为外键关联；
    4. 设备状态变更为 `Faulty`；
    5. 事务成功提交后，发布领域事件 `InspectionAnomalyEvent`，由异步事件驱动系统发送邮件和触发实时推送。

#### 风险 2：定时倒计时与到期邮件调度的“幂等性与漏发防范”
* **现象与技术隐患**：需求支持管理员配置多个提醒时间点（如提前 7天、3天、1天）。若维护后台调度服务出现异常崩溃、重启或集群多节点部署，可能出现：
  * 崩溃导致当天的提醒邮件彻底漏发；
  * 集群多个节点在同一时刻触发定时任务，导致收件人收到重复轰炸邮件。
* **深入反省**：
  * 不能仅依靠内存定时器（如简单的 `setTimeout` 或单机无状态定时器）。
* **设计补齐对策**：
  * 引入分布式任务调度与幂等记录机制。
  * 建立专用调度日志表 `maintenance_notify_log`，唯一索引约束为：
    `UNIQUE KEY (equipment_id, plan_id, target_notify_date, notify_stage)`
  * 每次调度执行时，采用数据库悲观锁或乐观锁防重，即便任务被多次调度或服务器重跑，同一设备的同一阶段提醒在当天绝不重复发送。
  * 每日清晨任务采用“区间补扫”策略，自动补发因服务器夜间维护错过的提醒。

#### 风险 3：知识库相似推荐的计算性能与冷启动退化
* **现象与技术隐患**：需求要求技术员在录入故障描述时，300ms 防抖实时展示最相似的历史案例。在系统投运初期，知识库仅有几十条甚至零条记录（冷启动）；而在长期运行后，故障单达数万条。如果每次前端按键都执行全表模糊扫描（`LIKE %xxx%`），数据库 CPU 将瞬间跑满。
* **深入反省**：
  * 纯 SQL 的模糊查询在文本语义匹配上表现极差，且无法给出量化的相似度百分比。
* **设计补齐对策**：
  * **冷启动策略**：当知识库少于 20 条时，降级为规则匹配：优先推荐同设备型号的常见保养手册条目与典型故障标记案例。
  * **成熟期计算策略**：
    * 采用结构化过滤 + 文本分词加权检索混合架构。
    * 先根据当前录入的 `equipment_id` 与 `equipment_type` 进行前置过滤，缩小候选集至前 100 条。
    * 后台维护轻量级倒排索引或向量嵌入缓存，利用 BM25 / 余弦相似度快速评分，提取 TOP-3。
    * 响应结果写入 Redis 缓存，Key 为 `hash(equipment_type + clean_text)`，缓存过期时间 10 分钟。

#### 风险 4：附件安全合规与工厂局域网大文件传输
* **现象与技术隐患**：现场巡检与故障处理强制要求上传高分辨率现场照片；设备台账允许上传几十兆的 PLC 备份程序与电气图纸。
* **深入反省**：
  * 如果在提交业务表单的同时通过 multipart 协议传输大文件，接口处理时间极长，移动端弱网极易断流失败。
  * 直接上传可执行程序可能引入恶意脚本或勒索病毒。
* **设计补齐对策**：
  * 实施**附件直传解耦模式**：前端先调用统一文件上传接口上传文件，服务端完成安全后缀白名单校验、MIME 类型嗅探、重命名为 UUID 并保存后，返回 `file_id` 与可访问 `file_url`；表单提交时仅传递轻量级 `file_id` 数组。
  * 设置文件魔数 (Magic Number) 校验，防止伪造 `.jpg` 后缀的可执行文件上传。

## 4. 三次反省成果总结与设计吸收清单

经过三轮深度反省，我们在后续的系统设计文档中吸纳了以下关键架构与业务强化项：

1. **工位快照与设备迁移机制**：巡检单与故障单持久化位置快照，支持资产随时在车间工位间流转而不破坏历史统计。
2. **多专业协同工单模型**：在严格的数据域隔离之上，开辟“机电一体化协作通道”，确保复杂故障协同无阻。
3. **状态机全生命周期联动**：设备停机自动挂起维护计划，报废设备自动注销待办任务，规避无效干扰。
4. **单事务强一致性联锁**：巡检提交与故障派生严格处于同一本地事务中，彻底消除数据断裂风险。
5. **分布式幂等定时任务体系**：建立发信防重日志表与状态位，实现维护到期邮件零重复、零遗漏。
6. **混合动力智能推荐引擎**：小样本规则匹配 + 大样本语义打分，配合 Redis 缓存，保障 500ms 内极速推荐。
7. **数据只读审计日志与软删除策略**：全系统严格禁止物理删除核心资产与用户，确保任何时刻审计回溯精准到人。
