## 1. 第一次反省：软件需求对系统需求的继承性、一致性与细化缺陷审查

### 1.1 审查目标与下沉视角
系统需求规格说明书（SRS）从宏观业务角度定义了 50 项系统级需求（REQ-USR-001 ~ REQ-NFR-005）。当系统需求落实为具体的“软件功能、UI 交互控件、前后端数据流校验”时，极易因抽象层级不同而产生需求缩水或边界模糊。本轮反省重点排查是否存在“系统有要求，但软件细化不足或边界缺失”的缺陷。

### 1.2 发现的具体缺陷与分析

#### 缺陷 1：11类设备专有参数在软件输入层的强校验缺陷
* **系统需求对照**：`REQ-DEV-004` 定义了 PLC、传感器、风机等 11 类设备的专有参数模型。
* **软件层缺陷剖析**：
  * 系统级设计允许使用 `JSONB` 存储额外参数，但这容易导致软件层彻底放弃数据有效性校验。
  * 若前端或 API 未对专有参数设置严格的校验模式（例如：用户在 PLC 的 IP 地址栏输入任意乱码、在风机额定转速输入负数、在电机的绝缘等级输入未定义的字符），脏数据将直接落库，导致后续全文检索与相似度匹配计算完全失效。
* **软件级整改措施**：
  * 在软件需求 `SWR-DEV-004` 中，定义分类型的强类型 Pydantic Schema（如 `PLCEquipmentParamSchema`, `FanEquipmentParamSchema`）。
  * IP 地址必须通过 IPv4 正则校验；功率、风量、转速等数值必须有物理范围约束（如 `gt=0`）；绝缘等级与信号类型限制为严格的枚举集合。

#### 缺陷 2：强制改密阻断机制在前端路由与状态机的穿透漏洞
* **系统需求对照**：`REQ-USR-004` 规定“新创建用户首次登录强制修改密码，改密完成前阻断所有其他功能访问”。
* **软件层缺陷剖析**：
  * 若仅在前端弹出一个改密 Modal 弹窗，技术人员可通过浏览器控制台手动关闭弹窗 DOM 节点，或直接通过修改浏览器地址栏 URL（如跳到 `/dashboard` 或 `/equipments`）绕过前端阻断。
  * 若后端接口未校验 Token 中的 `force_change_password` 标记，攻击者使用初始密码生成的 Token 可以直接调用所有的业务数据 API，形成重大安全穿透。
* **软件级整改措施**：
  * **后端双重阻断**：JWT Payload 必须包含声明字段 `"fcp": true`。全局权限认证中间件检查到该标记时，除了 `POST /api/v1/auth/force-change-password` 和 `POST /api/v1/auth/logout` 接口外，其余所有业务接口统一拦截并返回 HTTP 403，错误码 `10008: FORCE_PASSWORD_CHANGE_REQUIRED`。
  * **前端全局路由守卫**：Vue Router 全局 `beforeEach` 守卫强制重定向至 `/force-change-password`，并在该页面移除主导航栏和侧边栏菜单。

#### 缺陷 3：位置层级树的无限递归与循环依赖风险
* **系统需求对照**：`REQ-DEV-001` 规定“支持最多 5 级层级分类，仅叶子节点挂载设备”。
* **软件层缺陷剖析**：
  * 在软件接口修改节点的父节点时（Move Node），若未校验父子闭环（例如将节点 A 的父节点设置为其子节点 B），会导致树形结构形成环路（Cycle），引发前端渲染死循环和后端递归栈溢出崩溃。
  * 仅在前端控制 5 级层级容易被非法 API 请求突破。
* **软件级整改措施**：
  * 软件需求明确：后端在保存分类时，强制遍历 `tree_path`，校验新父节点不可存在于当前节点的路径中。
  * 强制计算 `level_depth = parent.level_depth + 1`，若 $> 5$ 则直接抛出参数异常，并在持久层利用唯一物化路径保障 O(1) 复杂度的层级检索。

## 2. 第二次反省：软件详细设计、高并发数据竞争与后台调度缺陷审查

### 2.1 审查目标与并发视角
工业制造现场虽然整体在线人数不如互联网海量，但在**特定交接班时刻、突发多点故障并发、以及定时调度批处理**时，极易产生高并发数据竞争与锁冲突。本轮反省重点审视软件详细设计中的并发模型、锁机制与调度鲁棒性。

### 2.2 发现的具体缺陷与分析

#### 缺陷 4：突发故障多人同时抢单认领的“脏写覆盖”缺陷
* **系统需求对照**：`REQ-FLT-004` 与 `REQ-FLT-005` 规定工程师接手处理故障单，状态从 `OPEN` 变为 `IN_PROGRESS`，记录接单时间。
* **软件层缺陷剖析**：
  * 当车间发生严重级别停机故障时，电气组可能有多位工程师同时在工作台收到弹窗并点击“接手处理”。
  * 传统的简单查询并更新：
    ```python
    fault = db.query(Fault).get(id)
    fault.status = "IN_PROGRESS"
    fault.assigned_engineer_id = current_user.id
    db.commit()
    ```
    会导致两位工程师均显示接单成功，最后提交的事务覆盖前一个，接单耗时与责任人记录被篡改。
* **软件级整改措施**：
  * 在软件详细设计中采用**原子条件更新 (Atomic Conditional Update / 状态乐观锁)**：
    ```sql
    UPDATE fault_records 
    SET status = 'IN_PROGRESS', 
        assigned_engineer_id = :user_id, 
        claimed_at = NOW(), 
        updated_at = NOW()
    WHERE id = :fault_id AND status = 'OPEN';
    ```
  * 检查 SQL 影响行数（`rows_affected`）。若返回 0，说明工单已被他人接手，向后点击者明确提示“该故障单已被 [工程师姓名] 认领”，彻底杜绝并发脏写。

#### 缺陷 5：海量设备维护倒计时大批量扫描的“内存溢出与事务悬挂”缺陷
* **系统需求对照**：`REQ-MNT-004` 与 `REQ-MNT-006` 要求每日零点调度推算所有设备倒计时并自动派发维护任务。
* **软件层缺陷剖析**：
  * 当工厂设备达到 1,000 台以上时，后台若直接使用 `equipments = db.query(Equipment).all()` 一次性将全量模型加载进 Python 内存，会导致内存突增。
  * 若在一个全局大事务中遍历处理所有设备，中间某一台设备因为数据缺失抛出异常，会导致整个事务回滚，导致所有设备的维护到期状态和工单全部无法生成。
* **软件级整改措施**：
  * 在软件详细设计中，后台调度任务必须采用**分块游标迭代 (Chunked Cursor Iteration, ChunkSize=100)**。
  * 每台设备的任务生成与状态跃迁采用**独立子事务或幂等 Upsert**，并结合 `try...catch` 进行单台异常隔离，记录错误日志而不阻断后续设备的批处理调度。

#### 缺陷 6：知识库推荐高频查询引发的“缓存穿透与雪崩”缺陷
* **系统需求对照**：`REQ-FLT-003` 规定在故障描述输入时 300ms 防抖实时推荐相似案例。
* **软件层缺陷剖析**：
  * 技术员可能输入现场生僻词或无意义字符，这些词在 Redis 缓存和数据库中均无匹配结果。如果每次按键都直接穿透到数据库执行文本向量计算，当多名技术员同时报修时，数据库 CPU 将瞬间飙升至 100%。
* **软件级整改措施**：
  * **空值短期缓存 (Cache Nulls)**：对于查询无匹配结果的输入，向 Redis 写入空数组占位符，TTL 设为 60 秒，有效防御恶意或无意义频繁查询对持久层的冲击。
  * **文本预清洗管道 (Text Normalization)**：在进入打分引擎前，软件层先去除无意义语气词与特殊标点，提升缓存命中率。

## 3. 第三次反省：软件接口契约、统一错误码体系与全流程鲁棒性审查

### 3.1 审查目标与鲁棒性视角
工业软件要求高度的自解释性与故障自愈能力。技术员在车间手持终端操作时，任何晦涩的网络错误或服务端 500 都会造成现场停顿。本轮反省重点排查软件接口错误码规范、文件孤儿清理机制与全链路鲁棒性。

### 3.2 发现的具体缺陷与分析

#### 缺陷 7：缺乏规范化工业业务错误码字典 (Error Code Dictionary)
* **系统需求对照**：`REQ-NFR-002` 与全局业务流程规范。
* **软件层缺陷剖析**：
  * 系统级设计中仅规划了标准 HTTP 状态码（200, 400, 403, 404, 500）。
  * 当技术员巡检提交失败时，若仅提示 `400 Bad Request`，现场人员无法判断是因为“漏填检查项”、“异常项缺少照片”、“设备已被停机”还是“网络超时”。
* **软件级整改措施**：
  * 在软件详细设计中建立标准的 5 位数字业务错误码体系：
    * `1xxxx`：认证与安全类错误（如 `10001: 账号已被锁定`, `10008: 必须修改初始密码`）
    * `2xxxx`：设备台账类错误（如 `20002: 存在子节点或下挂设备禁止删除`）
    * `3xxxx`：维护巡检类错误（如 `30002: 异常检查项必须上传现场照片`）
    * `4xxxx`：故障与 SLA 类错误（如 `40003: 工单已被接手`, `40006: 根因分析为必填项`）
    * `5xxxx`：系统与文件服务错误（如 `50001: 不允许上传可执行脚本`）
  * 所有接口统一返回标准化响应包：
    ```json
    {
      "code": 30002,
      "message": "检查项【传动轴润滑状态】判定为异常，必须上传现场照片证据",
      "data": null,
      "timestamp": 1725514800
    }
    ```

#### 缺陷 8：大文件直传解耦模式下的“磁盘孤儿文件泄漏”缺陷
* **系统需求对照**：`REQ-SYS-006` 附件管理规范。
* **软件层缺陷剖析**：
  * 为避免大表单提交超时，系统采用了“先上传文件获取 file_id，再提交业务表单”的解耦设计。
  * 若技术员上传了 5 张高清设备照片（共 40MB），但由于网络故障或临时退出放弃提交，这 40MB 的文件将永久滞留在磁盘且未与任何设备关联，日积月累导致服务器磁盘跑满崩溃。
* **软件级整改措施**：
  * 软件模型在 `equipment_files` 表增加 `is_linked` 状态标记，上传初始值为 `FALSE`。
  * 当业务表单（设备、巡检、故障）提交保存成功后，在同一事务中将对应文件标记为 `is_linked = TRUE`。
  * 后台配置定时清理守护任务 `clean_unlinked_orphan_files_job`，每日凌晨自动扫描并物理清理上传超过 24 小时但仍未关联的孤儿文件。

## 4. 三次反省发现的缺陷整改与软件设计吸收清单

经过三轮深度反省，我们在后续导出的**软件需求规格说明书 (SRS)**与**软件详细设计说明书 (SDD)**中，全面吸纳并落实以下 8 项重大软件工程改进：

| 序号 | 反省发现缺陷 | 影响范围 | 软件设计整改落地方案 |
|:---:|:---|:---|:---|
| **1** | 11类设备专有参数缺乏类型强校验 | 设备台账录入 | 引入分类型强约束 Pydantic 校验 Schema，对 IP、风量、量程设置正则与数值物理边界 |
| **2** | 首次登录改密易被前端路由绕过 | 账户与认证安全 | 后端 JWT 增加强制声明与鉴权过滤器拦截，前端路由全局守卫重定向 |
| **3** | 位置层级树修改父节点可能成环 | 设备位置树 | 后端增加路径闭环检测算法，基于物化路径严格校验层级深度 $\le 5$ |
| **4** | 故障并发接单脏写覆盖与耗时失真 | 故障接单流转 | 引入原子条件更新状态机乐观锁，第二位抢单者明确收到友好冲突提示 |
| **5** | 全量设备倒计时扫描内存溢出隐患 | 维护调度中心 | 采用 Chunked 游标分批处理，单台设备异常隔离，杜绝大事务崩溃 |
| **6** | 知识库高频推荐的缓存穿透与雪崩 | 智能推荐引擎 | 引入空值短期缓存（TTL=60s），前置文本预清洗与停用词过滤 |
| **7** | 缺少统一工业业务错误码字典 | 全局 API 通信 | 制定五位结构化错误码标准字典，所有端点统一返回带自解释错误文本 |
| **8** | 大文件直传遗留孤儿垃圾文件 | 附件存储服务 | 引入 `is_linked` 引用标记与 24 小时未关联文件自动清理后台任务 |
